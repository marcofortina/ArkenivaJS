# @arkenivajs/identity-spid

Optional Italian SPID federation contracts and validated profile policy. This package currently supplies the configuration foundation; it does not expose an operational authentication service or plugin yet. No login, federation verification, interoperability or accreditation is claimed.

Profiles pin registration, expected issuers, trust-anchor public keys and validity windows, metadata endpoints, required revocation and stale-metadata rejection, assurance levels, mapping identifiers and session lifetime. Configuration is captured as immutable data. The approved mapper catalog is keyed by `tenantMappingId`; each immutable profile binds its `identityMappingVersion` and profile ID to that configured mapping. Unmatched catalog entries are rejected.

The private policy capture rejects executable data properties, proxy inputs, malformed public keys, absent transactional store methods, insecure metadata URLs, cross-system assurance and missing providers. Parsing a public trust key does not establish federation trust. Cryptographic trust-chain, metadata-policy, dynamic revocation, protocol and identity checks belong to the authentication implementation and its independent tests.

Protocol integration uses the selected SAML/OIDC libraries. Technical rules and external conformance remain separate requirements: [Italian SPID/CIE OIDC rules](https://docs.italia.it/italia/spid/spid-cie-oidc-docs/it/versione-corrente/index.html).

Private federation statement verification uses JOSE for compact JWS signatures and required JWT claims, with exact issuer/subject/kid binding, fixed signature algorithms, finite input/metadata budgets and public-only descendant keys. Key validity bounds descendant evidence lifetime, and explicit JWK algorithm restrictions are retained. Signature evidence alone is insufficient to authorize federation participation: chain, metadata-policy and live trust-mark revocation checks must also succeed before an authentication implementation can issue identity.

Private metadata-policy resolution merges the standard `value`, `add`, `default`, `one_of`, `subset_of`, `superset_of` and `essential` operators before applying their specified order. Conflicts invalidate the policy, entity types remain isolated, and inherited mandatory parameters cannot become optional. The Italian profile's object-valued JWKS policy uses structural JSON comparison. Input data stays unchanged; executable input, unsupported operators and excessive structure or bytes fail closed. Rules follow the [OpenID Federation metadata-policy specification](https://openid.net/specs/openid-federation-1_0.html#section-6.1).

Policy defaults apply to parameters within an existing metadata entity type. A policy for an absent role does not create that role or impose its mandatory parameters on another entity type; policy merge conflicts still invalidate the chain.

OpenID Provider and OAuth Authorization Server issuer metadata must match the verified Entity Identifier in both the entity's signed self-configuration and the resolved metadata. Superior metadata and inherited policies cannot redirect that identity binding to another issuer or remove a mandatory issuer parameter.

Private federation document access uses the existing HTTP client with exact approved HTTPS endpoints, bounded request/response bytes, finite deadlines and a single transport attempt. Redirects, invalid UTF-8 and unexpected media types are rejected. Caller operation options cannot supply headers, methods or destinations; no user credentials are forwarded. Trust-mark status uses the OpenID Federation 1.0 POST form and signed-JWT media type. This transport returns documents for subsequent signature, chain and revocation validation. Native HTTPS tests trust their ephemeral CA only in an isolated child process; production and development reject private-network destinations.

Private trust-mark verification binds signature, issuer, subject, mark type and bounded expiry. Italian `id` and final Federation `trust_mark_type` claims are accepted individually; ambiguous combinations are rejected. Raw signed marks stay behind verifier-owned evidence and are returned only for an explicit status request. Status verification requires that verifier's exact mark, a correctly typed issuer signature, recent `iat` and the literal `active` state. Revoked, expired, invalid, stale and mismatched responses fail closed. These checks compose with chain and metadata-policy validation; they do not independently establish federation participation or application identity.

Private federation operations share one admission pool and one monotonic deadline per call. Provider work and actual JOSE promises retain their capacity until physical settlement, including after public timeout or shutdown cancellation. Normal calls require application readiness; internal bootstrap uses an explicit separate path. Unknown or executable operation options are rejected, and provider errors are normalized without retaining sensitive causes.

Private chain verification accepts an explicit ordered path rooted in configured keys, bounds the complete encoded input and delegation depth, and verifies each delegation and self-configuration using both superior-authorized and current published keys. A self-published key cannot expand superior authorization; root rotation requires a configured valid pin. Every applicable path-length and DNS naming constraint remains in force. Direct-superior metadata overrides only existing roles, entity-type filtering precedes inherited metadata policies, and Italian leaf-role constraints apply only to the leaf. Unknown critical extensions fail closed. The root configuration must contain the Italian profile's path bound. Returned immutable evidence is verifier-owned and expires with the earliest statement or signing key; it does not establish live membership, authenticate users or replace trust-mark issuer authorization and dynamic status checks. Constraint rules follow [OpenID Federation](https://openid.net/specs/openid-federation-1_0.html#section-6.2), with the Italian profile's additional root and leaf restrictions.

Private federation discovery inspects unverified configuration claims only to select explicitly approved document endpoints. Well-known configuration paths retain the entity's own path; arbitrary authority hints and fetch URLs grant no network permission. The entire operation shares cumulative byte, document, edge and depth limits and one deadline. Document caches last only for that operation. Each selected path must pass complete pinned chain and metadata verification; failed signatures, stale statements, loops or exhausted budgets never produce partial evidence. Timeout, cancellation and capacity failure stop the operation rather than initiating another path. Real HTTPS tests exercise configuration and subordinate-statement retrieval followed by native JOSE chain verification; dynamic role-specific membership and authentication remain separate required steps.

Private participation validation additionally requires a current accreditation mark for each intermediary and for the OpenID Provider. Italian mark identifiers bind the first path component to the defined entity role; a different role cannot substitute, even with a valid signature and active status. The selected anchor's signed `trust_mark_issuers` catalog must authorize the exact mark type and issuer. An external issuer requires its own same-anchor chain and live participation; circular accreditation cannot bootstrap trust. Issuer keys must be both delegated and currently published. Status endpoints come directly from authenticated issuer configurations and still require exact endpoint approval. Every verification repeats signed live status requests, within cumulative document and mark-attempt limits. Owned participation evidence expires no later than the earliest chain, mark, signing key or status freshness bound. Unsupported critical claims or trust-mark delegation fail closed. These private checks do not expose an authentication service or claim external accreditation; protocol callbacks, assurance, identity mapping and registration remain to be integrated.

Private login transactions use the existing Crypto service's AES-256-GCM envelopes and HMAC-SHA256 indexes with separate external `stateEncryptionKeyRefs` and `stateMacKeyRefs` catalogs. Each catalog contains one current reference followed by retained old references, up to eight; encryption, MAC and federation signing references must be disjoint. These optional configuration fields must be supplied together, and transaction operations fail closed when absent. No keys are derived from profile IDs or stored in application tables. Nonce, PKCE verifier, local return path and unverified tenant hint remain encrypted. State binds the complete immutable profile, mapping version, issuer, assurance, redirect, expiry and key references; a policy change requires a fresh login. The expiry uses the configured profile session lifetime. A shared atomic one-use claim must commit before protocol exchange receives the transaction; failed or lost persistence acknowledgements produce no success and are never retried automatically. Late decrypted plaintext is erased through physical cleanup. PostgreSQL tests exercise actual concurrent claims and lost acknowledgements using the built disposable security-state reference example. These transactions do not authenticate a subject or turn a tenant hint into authority.

Private signing-key loading reads only the activated profile's `signingKeyRef` through its captured external secret provider. Node imports PEM or PKCS#8 DER, validates key type and strength, and converts it directly to a non-extractable signing `CryptoKey`. Imported byte copies are erased; provider-owned bytes remain unchanged. Public metadata contains only the public JWK and its JOSE-calculated RFC 7638 thumbprint identifier, without private values or provider version labels. Unsupported algorithms, mismatched curves, weak RSA, expired material, executable provider data and provider failure deny import. Protocol callers must bracket later SDK signing operations with the loaded material's expiry check. Tests verify native JOSE signatures and an actual OpenID Client signed authorization request using the imported non-extractable key; no protocol engine or signing primitive is implemented locally.

OIDC profiles may supply typed `oidcRegistration` data for subsequent protocol integration: approved authority hints, received RP trust marks, organization metadata, explicit signature and encryption policies, an external decryption key reference and requested claim names. Automatic registration binds `clientId` to `entityId`. Organization contacts use the selected email validator; organization URLs require HTTPS and an optional logo requires an SVG path. Decryption, signing and state-protection references must remain separate. Capture makes bounded immutable copies and checks current RP mark syntax and subject without fetching documents or verifying accreditation signatures. Authentication must additionally verify those marks and their live status. Omitting this group preserves trust-only configuration compatibility; it does not supply an operational login registration. Required RP metadata follows the [Italian RP registration rules](https://docs.italia.it/italia/spid/spid-cie-oidc-docs/it/versione-corrente/metadata_oidc_rp.html).

Private response-decryption key loading uses that registration's external reference, the same guarded secret import as signing, RSA of at least 2048 bits and non-extractable native CryptoKeys limited to decryption. Only the configured RSA-OAEP or RSA-OAEP-256 variants are imported; public metadata exposes one encryption JWK with its RFC 7638 identifier. Key expiry must be checked around subsequent protocol work. Tests decrypt both prescribed authenticated CBC/HMAC JWE formats with native JOSE and exercise OpenID Client encrypted UserInfo with explicit signature checks enabled. Wrong subjects, foreign signatures and corrupted authentication tags are rejected. The SDK's default TLS processing alone does not satisfy the required explicit signature verification.

Private RP Entity Configuration generation signs the exact captured registration with JOSE and an explicitly typed `entity-statement+jwt` header. The self issuer and subject equal the registered entity; automatic client registration uses the captured callback, code grant and private-key JWT authentication. Public signing and encryption JWKs have distinct roles and thumbprints; two references resolving to the same key are rejected. Received marks keep their original identifier dialect. Expiry cannot exceed metadata refresh, mark or external key validity, and limits cover the complete encoded JWS including its signature. The output contains no private key, secret reference, version label or tenant hint. Publishing this self-configuration does not verify accreditation, supply a resolve endpoint implementation or expose an authentication service.

Private OIDC initiation composes fresh pinned federation membership, exact expected issuer and signed protocol capabilities with the protected transaction store and OpenID Client JAR generation. Only configured SPID assurance, S256 PKCE, automatic registration and approved algorithms are accepted. The signed request binds the captured client and callback, nonce, state and configured UserInfo claim names; its expiry is bounded by transaction, participation and key validity. Required outer HTTP parameters match the signed request. An unverified tenant hint and local return path stay inside encrypted state. Independent concurrent requests have distinct state and nonce; ambiguous storage or unavailable providers yield no redirect. This initiation helper does not exchange authorization codes, verify callbacks, map canonical identity or establish RP accreditation; those checks remain required before exposing an authentication service.

Credential-bearing protocol HTTP additionally requires an explicit `oidcRegistration.approvedProtocolEndpoints` catalog. It contains exact approved token, UserInfo and JWK-set HTTPS URLs, distinct from metadata discovery permissions. Omission preserves the existing foundations but cannot activate this transport. Protocol composition must match authenticated provider metadata against this catalog before supplying the SDK fetch hook. The hook uses the existing bounded HTTP client and native TLS, permits only form POST to the token endpoint and GET to UserInfo or JWKS, and rejects redirects, cookies, arbitrary headers, streaming bodies and excessive input. Bearer credentials are allowed only at UserInfo; they cannot reach JWKS. Response bytes and UTF-8 are checked before returning native Responses to the SDK. Code exchange has one attempt, including on 503. Production and development deny private-network destinations. Real HTTPS tests trust their ephemeral certificate only in an isolated child process; transport success alone does not verify token signatures or authenticate a subject.

Private OIDC callback verification accepts a bounded callback URL for the exact registered destination and fixed query values. Duplicate parameters, foreign issuers and executable objects fail before exchange. Protected state is atomically consumed before provider work; error callbacks and ambiguous acknowledgements cannot restore it. Fresh membership authorizes the provider metadata, then OpenID Client performs the code grant with the stored PKCE verifier and nonce, explicit signature verification and zero clock tolerance. Its private-key JWT assertion uses the Italian token-endpoint audience and a validity bound no later than current federation/key evidence. The exact registered redirect URI is retained in the form, including fixed query parameters.

ID Token and UserInfo encryption are checked independently against their registered policies before SDK decryption; a response cannot use the other endpoint's allowed algorithm as a downgrade. The SDK verifies ID Token and UserInfo signatures, issuer, client audience, subject and nonce. Additional Italian checks cover `at_hash` with native SHA-2 and constant-time comparison, ID Token `nbf`/`iat` and UUID identifiers, and actual Access Token JOSE signature, subject, client binding and UserInfo audience. Only declared requested UserInfo attributes enter the result. Strings remain unchanged; booleans and finite numbers use their scalar string representation, and nested objects fail closed. Returned assurance cannot be below the requested level and must remain in resolved provider policy; a permitted higher level is retained. Evidence expires with the earliest provider token, live federation, key or transaction bound. Copied, foreign-verifier and expired results cannot enter later mapping. Native HTTPS tests exercise real signed/encrypted exchanges, wrong claims and signatures, replay, concurrency, revocation and provider/persistence failure. This helper returns verifier-owned upstream evidence; canonical tenant mapping, RP accreditation and the public authentication lifecycle remain required. Signed JWK-set source integration is still pending.
