# @arkenivajs/security

`createAuthService(options, operation?)` creates an owned OIDC resource-server verifier. `securityPlugin(options?)` configures `app.auth` from root `security:{issuer,audience,tenantClaim?,algorithms?}`. Declare logging explicitly, and declare `security` in the API plugin's dependencies. Initialization discovers the configured issuer's metadata unless a trusted `jwksUrl` is supplied. Module import opens no connection. Close the standalone service or stop its application to release the private HTTP agent and invalidate issued contexts.

Issuer matching is exact, including a trailing slash. Discovery must return the configured issuer and a JWKS URL within the issuer origin or an explicitly configured `allowedJwksOrigins` entry. HTTPS, CA/hostname verification and TLS 1.2 minimum apply. Requests allow two connections, a 512 KiB response and a five-second network deadline, with no redirect or automatic retry. Private addresses are blocked by default. `allowInsecureLoopback:true` is restricted to development/test and literal loopback HTTP URLs; it must never appear in production policy.

The default asymmetric algorithm allowlist is `['RS256']`. Supported explicit alternatives are RS384/512, PS256/384/512, ES256/384/512 and EdDSA. Symmetric HMAC and unsigned tokens are rejected. Verification requires signature, subject, issuer, destination audience and expiration, and enforces `nbf`. Default `tokenType:'JWT'` supports issuers that use JWT access-token headers; set `'at+jwt'` for an issuer using the access-token profile. Register an API-specific audience and never configure an ID-token/client audience. Clock tolerance defaults to five seconds, bounded to 0–60.

`verifyBearer(header, options?)` accepts one compact bearer assertion up to 16 KiB. Missing assertions use `EK_AUTH_REQUIRED`; invalid/mismatched assertions use `EK_AUTH_INVALID`; cancellation/deadline use `EK_ABORTED`/`EK_TIMEOUT`. Returned identities are deeply immutable. `scope` or `scp` must be a space-delimited string, bounded to 4096 characters. `requireScope(identity, scope)` checks exact membership and rejects objects that did not originate from this verifier with `EK_AUTH_FORBIDDEN`. Unknown signing keys trigger JOSE's bounded cache refresh: default cache age 300 seconds and cooldown 30 seconds; production cooldown cannot be disabled. Do not reduce these controls to accommodate arbitrary caller keys.

`tenantFrom(identity)` reads exactly one configured claim (default `tenant_id`), bound to an issuer/audience-verified identity. Tenant values are 1–128 ASCII letters/digits or `.`, `_`, `:`, `-`, beginning with a letter/digit. Missing, empty, array-valued or malformed claims reject with `EK_TENANT_UNVERIFIED`. The optional synchronous `authorizeTenant(identity, tenantId)` must explicitly return true when configured. Multi-tenant selection requires an application authorization flow that issues a new single-tenant assertion; request headers and baggage cannot select a tenant.

`isVerifiedTenant(value)` checks verifier-local runtime provenance and current token validity. A TypeScript cast, object clone, object from another verifier or closed/expired verifier cannot establish trust. Never serialize this context and assume its brand survives a trust boundary. Destination services must independently verify a service access token with their own audience. Tenant context does not add SQL predicates or row isolation automatically; applications must scope every data access and cache key.

`close(options?)` invalidates identities and contexts, aborts pending key transport and closes its agent. Individual verification deadlines stop the caller's wait; a shared JWKS fetch can remain bounded by its own five-second deadline for other concurrent callers. No late verification result is registered after cancellation or closure. Authentication observations and plugin logs record only outcome/error code, excluding credentials, subject, claims and tenant. A failing observer increments `observerFailures` without changing authentication. `stats()` reports verified/rejected/observer-failure counts, not a durable security audit.

Tests sign real RSA assertions and serve discovery/JWKS on disposable loopback sockets. They verify signature/issuer/audience/algorithm/time/type failures, rotation, concurrent verification, claim ambiguity, spoofed headers/baggage, immutable provenance, cross-application isolation and bounded cleanup. The REST isolation example uses tenant-filtered in-memory records; SQL/RLS isolation requires database-specific integration tests.

`assuranceResolver(identity)` is an optional synchronous, trusted issuer-specific policy, also accepted in root security options. It runs only after signature, issuer, audience, time and token-type verification. It must explicitly map that issuer's documented authentication claims and enforce the required freshness using trusted time; unrecognized or missing proof must return `single-factor`. There is no built-in interpretation of claims named `mfa`, `amr` or `acr`, and no session/token issuance. A missing resolver leaves `Identity.assurance` absent. Invalid decisions or exceptions fail closed with `EK_MFA_POLICY`.

`requireAssurance(identity, requirement)` accepts `single-factor`, `mfa` or `phishing-resistant` in increasing order. It requires a current identity owned by this verifier, rechecks the configured policy's freshness and cannot upgrade the original decision. Cloned, foreign, expired or insufficient identities reject with `EK_MFA_ASSURANCE_REQUIRED`; a closed verifier uses `EK_RESOURCE_CLOSED`. TOTP and recovery proof must never map to phishing resistance. Local factor evidence must first be consumed and bound to a subject by an application session authority, rather than constructing an identity or treating serialized evidence as a bearer credential.

`hasAssurancePolicy()` is the managed provider's startup capability check. The API requires it to return true before binding any listener with assurance-protected routes. Custom authentication adapters must supply the same check and the normative `requireAssurance` method; a failed check never permits startup. This check grants no request authorization. An actual issuer mapping still controls each decision. Optional factor services have separate implementation and acceptance gates.
