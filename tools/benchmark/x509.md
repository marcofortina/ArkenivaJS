# Certificate utilities: isolated native comparison

This exploratory smoke compares native certificate utilities and the public
X.509 adapter in four sequential worker processes: BASELINE, FRAMEWORK,
STANDARD and DETAILED. It rejects `--full` and never starts deferred repeated
campaigns or the one-hour soak. `releaseGate` is always false.

```sh
pnpm build
pnpm --filter @arkenivajs/benchmark-foundation x509 --smoke /private/existing-parent/new-certificate-report
```

Use a fresh normalized absolute destination outside the product repository.
The directory is 0700 and its report is 0600; an existing destination is never
overwritten. The runner uses the built disposable certificate example and the
existing OpenSSL binary. It installs no operating-system package or service.

Private `*-observations.json` files retain completed worker metrics after a
material-leak check, even if workload validation fails. They are explicitly
`UNVERIFIED`, include the source/dirty state and observed parent trust-check count,
and never substitute for a validated final `report.json`. Scheduling, saturation
and completion failures are reported before exact trust-read equality. All load,
trust, cleanup and privacy requirements remain enforced.

The parent creates one ephemeral CA, leaf certificate, CRL and loopback TLS
endpoint. Each worker receives identical public DER through closed IPC. Private
keys stay in the parent fixture. Every profile uses the same actual pinned-CA
TLS/CRL authority through the same IPC request path; a cached or simulated
revocation result is not substituted for a handshake. Exactly 55 trust checks
per profile cover five warmup calls and fifty measured calls without retry.

Four scenarios exercise parsing, expiry arithmetic, fingerprints and complete
trust inspection. Native parsing constructs an actual `X509Certificate`, while
the adapter additionally builds bounded immutable metadata. Native expiry and
fingerprint calls use a certificate parsed during setup; the adapter uses its
corresponding parsed metadata. Native chain inspection calls the same
independent TLS/CRL authority directly; the adapter also performs its configured
admission, preliminary linkage/hostname and response-binding checks. The
baseline does not emulate those added contracts or claim that signature checks
alone implement full PKI verification.

Each scenario has five warmup calls followed by fifty fixed offers at fifty
operations per second, with concurrency one. Missed schedules and saturation
are counted without queueing or catch-up bursts. A smoke requires all offered
operations to succeed without drops. Results include individual latency
samples, p50/p95/p99/max, achieved rate, scheduling lag and certificate input
bytes per second. These input bytes are not TCP wire traffic or application
request bodies.

STANDARD uses actual SDK metrics and 10% trace sampling; DETAILED uses full
sampling and a span around every actual trust-provider call. The adapter's own
trust-inspection span is used directly; it is not wrapped by a duplicate
benchmark span. Pure utility scenarios use an explicit application measurement
span, because their synchronous public APIs create no internal asynchronous
span. FRAMEWORK disables diagnostics and BASELINE calls native utilities.

The bounded loopback OTLP JSON receiver requires actual traces and metrics in
the enabled profiles and checks their complete bodies in memory for certificate
metadata, fingerprints and public corpus encodings. The report persists only
safe aggregates, never raw certificate/OTLP bodies or the ephemeral comparison
fingerprint set. Unknown worker output fails the run. The receiver allows eight
concurrent requests, one MiB per body and 32 MiB in total; workers have a
60-second watchdog.

Worker CPU, RSS/heap samples, GC and event-loop observations are process totals
including setup, warmup, conformance checks, paced waits, SDK work and flush.
Conformance checks run outside the operation latency timer but inside the
resource window. Ten-millisecond samples cannot establish exact transient
memory peaks. Parent CPU is recorded separately over each whole worker
lifetime; it includes the shared TLS authority, IPC, report handling and OTLP
receiver together. Parent RSS uses boundary observations only. These different
windows are explicit and must not be summed into exact per-operation usage.

Hardware, source commit/dirty state, Node/OpenSSL/FIPS state and profile order
seed 137 are retained. There is one exploratory iteration and no independent
repeat confidence interval. Exact exporter retries remain null; repeated OTLP
bodies are only observed repetitions. Receiver acknowledgment does not prove
durable collector storage. Native client/provider sockets, workers, timers,
listeners, temporary CA material and owned key buffers are cleaned up.

Actual adapter/SDK tests separately verify successful and rejected certificate
operations export correctly under the unchanged common label policy, with no
private metadata or dropped diagnostics. This smoke is evidence of the recorded
local workload, not production capacity, a calibrated regression gate or
certification of an external CA/OCSP service.
